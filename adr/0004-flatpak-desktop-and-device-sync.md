# ADR 0004: Rust Core, Flatpak Desktop App and Device Sync

## Status

Accepted on 2026-10-12. Supersedes these parts of
[ADR 0003](0003-local-first-without-server.md): server mode kept until
feature parity, the AppImage and .exe targets, the server/local toggle on
iPhone, the open decision on accounts, and the phone backend approach.

## Context

GoonCave runs as a self-hosted server: Docker Compose files, images on GHCR,
a Linux installer that sets them up, multi-user accounts with login, and an
iPhone app that opens the server's website. Moving data between devices
works only through that server. The backend is about 24,000 lines of
TypeScript run by Bun; the tagger is a separate Python service.

ADR 0003 moved every platform to local apps but kept the server until the
local apps matched it.

## Decision

- **No server.** Remove the Compose files, the GHCR images, the PC
  installer, remote access, accounts and login. Nothing replaces them before
  the first desktop release: there is no app to download in between.
- **One owner per device.** No accounts and no login.
- **One Rust core on every platform.** A Rust core replaces the Bun backend
  and the Python tagger. It keeps the existing HTTP API contract, served on
  the device only, so the React interface does not change. The desktop app
  is its first user; phones follow. The Bun backend and the Python tagger
  were deleted once the core covered every feature.
- **Shell: one thin window per platform, calling the Rust core directly, with
  no Swift or Kotlin bridge.** Linux is a GTK4 window with WebKitGTK
  (`webkitgtk-6.0`), because Tauri's GTK3 WebKit scrolls jerkily (see the
  shell test results). iPhone is Tauri. Windows is Tauri on WebView2, which
  is Chromium and has no GTK, when Windows is supported.
- **Desktop app:** Linux ships as a `.flatpak` file attached to the GitHub
  Release; Flathub is not a target yet. Windows ships as a Tauri `.exe`
  installer when it is supported. If Tauri stops working on the desktop, the
  fallback is Electrobun with bundled CEF, if its Flatpak output produces a
  working app, then Electron.
- **iPhone app:** standalone only, on the Rust core. The server client is
  removed. iPhone builds run on hosted macOS in CI and produce an unsigned
  IPA; no Mac is needed.
- **Sync between devices:** every app connects to a WebDAV folder, and later
  to Google Drive. Details: [docs/sync.md](../docs/sync.md).
  - On every start the app reads the remote copy and merges new data.
  - It uploads a few seconds after each change and again when it closes.
  - One backup per day; the last 14 are kept.
  - Synced: database, tags, favorites, settings, votes, read marks, WD14
    tags and found sources.
  - Records are matched across devices by file `sha256`, because file `id`
    is generated by each device.
  - Conflicts: the most recent change to a record wins.
  - Media files: an option, off by default. Each file is stored once, named
    by its `sha256`. The setting shows the space needed before it starts.
  - Booru credentials never leave the device.
- **Heavy work is shared.** A device skips files another device already
  tagged or matched. Desktop apps keep working from the system tray. Phones
  process only what is left, in resumable chunks inside iOS background tasks.
- **Versions:** Linux and Windows share one desktop version, tagged
  `desktop/v<version>`. On every platform, `1.0.0` is the Rust version
  with full parity with the old app; earlier versions are `0.x`. Every existing GitHub Release
  and version tag (PC and iPhone) is deleted; versions start again.

## Constraints found

Verified on 2026-10-12:

| Fact | Consequence |
| --- | --- |
| iOS suspends WKWebView JavaScript in the background. Capacitor Background Runner runs separate JavaScript without web APIs, up to 10 minutes per task. | The TypeScript backend cannot run in the background on iPhone; native code can. |
| Developer reports show CPU and Neural Engine work 4–5× slower in an iOS background task, and no background GPU on iPhone. | Phone processing is chunked and resumable; desktops do most heavy work. |
| Bun cannot run on Android ([oven-sh/bun#30766](https://github.com/oven-sh/bun/issues/30766)) or iOS. | Phones cannot reuse the Bun backend. |
| The development database is 160 MB with 369 files, mostly the tag database (97,000 aliases, 198,000 implications). | In-memory SQLite (sql.js) is ruled out; every platform uses native SQLite. |
| `files.id` is random per device; `files.sha256` is the content hash. | Sync keys on `sha256`. |

## Shell test results

Both test builds come from `spikes/tauri-shell` on the branch
`spike/tauri-shell`.

| Platform | Result | Consequence |
| --- | --- | --- |
| Linux Flatpak (GNOME 51 runtime, WebKitGTK 4.1) | The app runs. H.264 and VP9 videos fail when loaded through the `tauri://` protocol and play when served over HTTP. | The core serves media over local HTTP. |
| Linux scrolling (GNOME on Wayland, display scale 2 with 125 % text, Intel Arc + NVIDIA, 240 Hz) | Every page scrolls at a steady 60 fps with no long JavaScript tasks, yet looks jerky, in the Flatpak and in the native build alike. A 15-line GTK3 + `webkit2gtk-4.1` window without Tauri is as jerky; the same window on GTK4 + `webkitgtk-6.0`, GNOME Web and Chromium are smooth on the same page. Thumbnail caching, `backdrop-filter`, the GPU in use, `WEBKIT_DISABLE_DMABUF_RENDERER` (worse), `WEBKIT_DISABLE_COMPOSITING_MODE`, `WEBKIT_FORCE_COMPOSITING_MODE` and `GDK_DPI_SCALE` change nothing. | The cause is WebKitGTK on GTK3, which is the only variant Tauri supports on Linux. Do not look for it in the frontend or the core. A fix is a GTK4 + `webkitgtk-6.0` desktop shell or the fallback below. |
| Linux view transitions (same machine, GTK4 shell and GNOME Web alike) | Opening or closing a file animates at 35–45 ms per frame in a 1200×800 window at display scale 2 (2400×1520 pixels) and at 60 fps in a quarter-size window: the cost is about 10 ms per megapixel of window, whatever the CSS. Hiding the picture, removing shadows, filters, the root fade and the blend mode, forcing hardware acceleration, and Skia's CPU or GPU painting threads change nothing. The first open after launch also waits about 300 ms before the first frame; Chromium takes the same 300 ms but keeps showing the old page meanwhile. | The engine composites a full-window view transition at CPU speed. A cheaper page animation on desktop Linux is the lever; no CSS override on the transition itself helps. |
| iPhone (unsigned IPA re-signed with KravaSign) | The app installs and calls Rust. Typed View Transitions, swipe between pictures and the side menu work. | Tauri is the phone shell. |
| iPhone back and forward edge swipe | Off by default in Tauri, with no setting ([tauri#13367](https://github.com/tauri-apps/tauri/issues/13367)). | The app turns on `allowsBackForwardNavigationGestures` on the WKWebView at startup. |
| iPhone status bar | The web view fills the screen, so the header sits under the status bar. | The frontend pads the top with `env(safe-area-inset-top)`. |

## Consequences

- No app to download until the Rust core covers every desktop feature.
- Multi-user libraries and access from other devices end.
- Server API compatibility (`apiVersion`) no longer matters.
- `sharp`, `argon2`, onnxruntime under Bun and the Python tagger leave the
  product, together with their known Windows and packaging problems.
- Sync replaces export/restore and server transfer as the way data moves
  between devices.
